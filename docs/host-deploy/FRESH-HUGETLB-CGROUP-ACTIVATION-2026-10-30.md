# HugeTLB controller prerequisite — protected systemd 252 activation

**2026-10-30 — source-only candidate. Native activation NOT executed. Compiler admission NO-GO.**

Owners: root-control Regular + host-deploy Regular. Tracking [root-control #11](https://github.com/zog144/root-control/issues/11) and [host-deploy #5](https://github.com/zog144/host-deploy/issues/5).

## Native failure and ownership

Disposable systemd 252 Work observed `hugetlb` in the kernel but not enabled in the ancestor `cgroup.subtree_control`. Consequently the dedicated `/sys/fs/cgroup/zogfreshcrossbootstrapoct25.slice` lacked `hugetlb.*.max` limits. The existing verifier rejected the request correctly; no worker canary was launched.

systemd 252 does not expose `hugetlb` among its supported `Delegate=` controller names. The fresh slice is a single-level systemd slice immediately beneath the root cgroup2 hierarchy. Enabling `+hugetlb` in the **PID1-owned root** `cgroup.subtree_control` affects the shared root's children, not only the fresh slice. This is not safe to do silently during `arm`, worker start, watchdog or reboot recovery. It requires explicit, independently authorized host-owner approval and native preflight. No default manager setting or generic root-control RPC changes that fact.

## New source flow (does not mutate a host merely by existing in the repo)

1. **Read-only preflight:** `fresh_hugetlb_activation.snapshot()` verifies exact cgroup2 root mount and one-level dedicated slice, root ownership/nonwritable ancestry, fixed inode/device, kernel availability, `cgroup.controllers`, `cgroup.subtree_control`, inherited controller visibility and kernel limit-file names. Symlinks, mount substitution and unknown controller inventories fail.
2. **Fresh operator approval:** independently inspect shared PID1 service state and the original historical baseline. Host owner must install *its own* protected root:root mode 0600 `STATE/hugetlb-ancestor-approval.json`, distinct from ordinary compiler admission. Exact fields are `schema=host-deploy-fresh-hugetlb-root-approval-v1`, `status=operator-approved`, `host_id`, `boot_id`, `plan_sha256`, `slice_unit`, `scope=dedicated-fresh-slice-with-explicit-shared-root-controller-change`, `allow_shared_root_change=true`, and four integer `root_device/root_inode/slice_device/slice_inode` plus `root_subtree_sha256` from an independent snapshot. **A saved receipt or previous authorization cannot generate this approval.** Changes to shared-root controller policy require their own operator approval even on a disposable host.
3. **Single selected operation:** protected native owner `python3 -B -m zog.host_deploy.gateway.fresh_native_owner activate-hugetlb`, **not** available via a generic RPC or controller request. It checks root and actual PID1 systemd 252, exact installed sidecar plan/source and historical baseline, still active exclusive sidecar PID, matching boot and approved slice identity, verifies protected approval, and either confirms an already enabled root controller or writes ONLY fixed `+hugetlb` to the cgroup2 root. No `-hugetlb` and no arbitrary ancestor or sibling writes. Afterward it checks that kernel limits appeared, then stores a separately protected, durable `hugetlb-activation.json` with `status=activated-needs-native-review`. A partial kernel mutation or failed receipt remains UNCERTAIN; **never automatically roll back a PID1-owned shared-root controller**.
4. **Arm remains separate:** ordinary `arm_approved()` must independently read the protected activation receipt, verify exact Host/boot/plan and root/slice inode/device, confirm ancestor and child controller state and all expected limit paths, then call the strict existing `seal_hugetlb_before_arm()` to write and read back every `hugetlb.*.max` and reservation limit at 0. Missing files or changed slice → NO-GO.
5. **Independent root-control gate:** `fresh_start_gate.hugetlb_ready()` reads the *current* root `cgroup.subtree_control`, fresh slice `cgroup.controllers`, every `hugetlb.*.max` and `hugetlb.*.rsvd.max`; all must exist in correct pairs and equal 0. It checks **both before the durable one-shot worker claim and immediately before PID1 StartTransientUnit**. It never enables an ancestor controller.
6. **Lifetime and reboot:** if systemd unloads/recreates the transient slice, inode change invalidates the receipt; if systemd changes the ancestor controller state, native readback blocks. The existing `recover()` deliberately does **not** reactivate the controller, transient sidecar, budgets or jobs after reboot. A new boot needs fresh protected installation/approval/readback and separate native acceptance; do not replay the old request.
